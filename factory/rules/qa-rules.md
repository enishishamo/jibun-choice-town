# QA規約（JC FINAL QA用）

実装後、以下を評価する。評価結果は `factory/projects/<world-id>/qa-report.md` に保存。

## チェック項目

1. ファーストビュー（イベント入口が魅力的か、何をすればいいか分かるか）
2. 操作の分かりやすさ（説明なしで触り始められるか）
3. C利用（道具・情報カードを見ないと解けない作りになっているか）
4. 操作→結果（操作が結果に反映されるか。固定クリアがないか）
5. retry（失敗→再試行の導線があるか）
6. Job Reveal（discoveryEcho が「さっきの行為」を正しく指しているか）
7. interestSeeds（実際にした行為だけが選択肢になっているか）
8. スマホ（縦画面で操作できるか。ドラッグ系はタッチで成立するか）
9. 画像切れ（ホットスポット・シーン画像のクロップ崩れ）
10. 画像の粗さ（表示サイズに対する解像度不足）
11. 既存UIとの一貫性（共通シェル Q1Screen の流儀に沿っているか）
12. 既存ゲームの回帰（registry.ts / data/index.ts への追加が既存編を壊していないか）
13. FACT_CHECK_REQUIRED（未解決フラグの残数と内容）

## 検証手段

- `npm run build`（tsc + vite build が通ること）
- `npm run lint`（oxlint）
- `npm run dev` + ブラウザ確認（town-app 設定、port 5177）
- `node factory/scripts/update-factory-db.mjs`（DB再同期と整合性チェック）

## ゲート検査の書き方（2026-09-21 追加・canonical）

**ゲートの検査は「ソースの見た目」ではなく「実際の挙動」を観測すること。**

2026-09-21 の独立レビューで、給食編の QA ハーネスが「総合点を出さない」「正誤を
出さない」「勝手にクリアしない」の 3 つを *ソースの grep* で検査しており、
わざと壊した実装（盤面に生の数値を描画／「できた！」「まだだよ」を描画／
「きみは〜にむいている」という適性の断定を描画／`place()` の中で自動クリア）
を **すべて PASS させていた**。当時このハーネスは「51/51 checks passed」を出力し、
それが task の qa_evidence として記録されていた。

したがって:

1. **不変条件は駆動して確かめる。** 「X 以外で状態 Y にならない」は、その状態機械に
   取りうる操作を全空間に当てて確かめる。「Y にする呼び出し」を grep しない
   （書き方を変えれば正規表現は素通りする）。
2. **表示は実ブラウザで収集し、allow-list と突き合わせる。** 禁止語の blocklist では
   なく、「文言モジュール（copy）に載っている文字列だけが描画されている」ことを
   検査する。aria-label も対象に含める。
3. **スクリーンショットのランは全状態を検査する。** 最後の 1 枚だけでなく、撮影した
   すべての状態で「開発用マーカーが画面に出ていない」「出してはいけない内容
   （例: PLAY 前の職業名）が出ていない」「読み込みに失敗した画像がない」を検査する。
   画像の欠落は 4xx にも文字列にもならず、CSS のフォールバックに化けて素通りする。
4. **ソースの grep は「ドキュメント検査」としてなら記録してよい。** ただしゲートでは
   なく、検査名にドキュメント検査であることを明記する。
5. **標本は標本の隙間を見られない。** スクリーンショットや定点観測では、アニメーション
   中だけ出る表示（飛行中の点数、演出中の正誤）を取り逃がす。走行中ずっと蓄積し
   （MutationObserver 等）、蓄積した全体に対して検査する。
6. **こちらが操作するテストは「何も起きないこと」を証明できない。** ハーネス自身が
   ジェスチャを送っているなら、何も触らない時間を明示的に作り、その間に状態が
   進まないことを検査する（＝子どもが観客になるビルドを弾く）。
7. **検査対象が0件だった検査は、通ったのではなく空振りしている。** 対象数を数え、
   ありえない少なさなら検査自身が落ちること。合格と空振りは見分けがつかない。
8. **対応すると謳った画面サイズ・メディア設定・言語は、ランのパラメータにする。**
   報告書の一文にしてはいけない。手で開いて目で見て「入っていた」と書くのは検査
   ではない。全部を毎回回せないなら、assert を減らすのではなく「対応する」と言う
   範囲のほうを狭める。（2026-09-22 r4: 5サイズ対応と書いてあったが実際に回して
   いたのは1サイズだけで、初めて全サイズを assert したら 320x568 でタップ領域が
   44px を割っていた。4回の独立レビューと手動確認をすり抜けていた）
9. **再現しなかった指摘は「間違い」ではないが、再現しなかったことを記録する。**
   その上で直したなら、なぜ直したのかも書く（多くは「たまたま通っていただけの検査
   を偶然に依存させないため」）。書かないと、後から変異を再実行した人が「修正前でも
   落ちる＝修正は無意味だった」と誤読する。

上の 1〜9 はすべて、意図的に壊した実装（変異）を投入して「落ちること」を確認済み。
新しいゲート検査を書いたら、同じように変異を1つ作って落ちることを見てから記録する。

実装例: `factory/harness/gameplay-qa-v2-lunch-menu.mjs`、
`factory/harness/v2-lunch-shots.mjs`。
経緯: `factory/state/retrospectives/2026-09-21-nutrition-teacher-slice.md` §2。

## 分類

- **CRITICAL**: 進行不能・既存編の破壊・重大な実務誤認
- **HIGH**: 禁止事項違反（C不要で攻略可能、固定クリア等）
- **MEDIUM**: 分かりにくい操作、画像品質、文言
- **LOW**: 微調整

修正可能なものは修正案まで作成する。
