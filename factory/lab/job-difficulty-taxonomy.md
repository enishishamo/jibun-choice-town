# Job-Specific Difficulty Taxonomy — 仕事固有の難しさの分類

Game Design の起点。**「面白い mechanic を仕事へ貼る」のは禁止**。
まずその仕事の実務が「何ゆえに難しいのか」をここに分類し、
difficulty → mechanic の順で `taxonomy/job-mechanics-map.json` から候補を引く。

各 difficulty には id / 説明 / 実務での現れ方 / 子ども向け翻訳の指針 を持たせる。

| id | 難しさ | 実務での現れ方（例） | 子ども向け翻訳の指針 |
| --- | --- | --- | --- |
| incomplete_information | 情報が不完全なまま判断する | 診断（検査結果は一部）・与信審査・災害対応 | 「調べる行動」に予算を付け、全部は調べられなくする |
| simultaneous_demands | 同時に複数へ対応する | 看護・厨房・管制・接客 | 2〜3件の同時進行に絞り、放置のコストを見せる |
| prioritization | 優先順位を決める | トリアージ・修理受付・配送順 | 「全部はできない」を明示し、選ばなかった側の結果も見せる |
| safety_tradeoff | 安全性と効率のトレードオフ | 工事工程・食品衛生・被ばく管理 | 安全側に倒すと進まない/コスト増を実感させる |
| limited_resources | 限られた資源の配分 | 予算・人員・薬剤在庫・電力 | 資源メーターを1本見せ、使い切り＝失敗にする |
| time_pressure | 時間制約の中で動く | 手術・報道・災害・締切 | リアルタイムは短く。ターン制の「期限」でも成立する |
| spatial_arrangement | 空間配置が結果を決める | 会場設営・積載・都市計画・売場 | 置く→試す→直すのシミュレーション往復にする |
| dynamic_state | 状態が刻々と変わる | 患者容態・天候・相場・交通 | 状態変化を1〜2変数に絞って可視化する |
| counterpart_variability | 相手によって正解が変わる | 接客・教育・介護・営業 | 相手カード（意向・体質・事情）を読ませ、同じ操作でも結果を変える |
| trial_and_error | 試行錯誤でしか到達できない | 研究・レシピ開発・デバッグ | 試行にコストを付け、結果から次の仮説を立てさせる |
| oversight_risk | 見落としが致命傷になる | 検品・校正・監査・投薬照合 | 「どこを見るか」を選ばせ、見なかった場所にリスクを残す |
| prediction | 先を予測して手を打つ | 需要予測・仕入れ・防災・農業 | 予測材料（C）を見せ、当たり外れが結果に出るようにする |
| quality_judgment | 成果物の良否を自分で判定する | 撮影・調理・製造・演奏 | 「これで届けてよいか」の自己判定をゲート化する |
| irreversibility | やり直しがきかない | 手術・放送・建設・法的判断 | 回数予算・確認工程で「取り返しのつかなさ」を表現する |

## 使い方

1. 対象職業の research.md から、その仕事の難しさを上記 id で 2〜4 個特定する
2. `taxonomy/job-mechanics-map.json` で各 difficulty に適した mechanic 候補を引く
3. 候補 mechanic を 2〜4 案の設計へ展開し、独立比較（Claude 案 × Codex 評価）で選ぶ
4. 選ばれなかった難しさも E 画面や演出で言及できないか検討する（体験の厚み）
