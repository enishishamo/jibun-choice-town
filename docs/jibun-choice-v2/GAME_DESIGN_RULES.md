# GAME DESIGN RULES — Ver.2（PLAY FIRST）

制定: 2026-09-20（Human Decision）。`factory/rules/principles.md` / `game-design-rules.md` の
上に積む Ver.2 固有の規約。矛盾する場合は本書（Human Decision）が優先。

## 1. PLAY FIRST の設計規約（LOCKED）

1. **説明画面を先に置かない。** ゲームは「触れる状態」から始まる。
2. 最初の 1 タップで**何かが起こる**。操作直後に画面・世界が反応する。
3. **もう一度触りたくなる**構造にする（結果が変わる／もっと良くできる余地がある）。
4. 職業名・仕事の説明は**後出し**（Job Reveal は遊んだ後）。
5. ゲームにするのは「仕事の説明」ではなく、**その仕事で実際に行っている行為**。
6. 絵・動き・反応で伝えられることは文字にしない（UI/TEXT RULE）。
7. 判定に必要な情報を「開かないと見えない場所」に隠さない
   （Ver.1 の InfoCards 依存型は作らない。情報は盤面そのものに置く）。
8. 0/1 の正解判定より、**改善型**（もっと良くなる）を優先する。
   ただし、正解が一つしかない実務（安全基準など）を無理に改善型にしない。
9. 失敗は「即答の文章」ではなく、**世界の反応**で返す（principles.md と同じ）。
10. 適性判定・タイプ分類をしない（Mission）。

## 2. Ver.1 から引き継ぐ骨格

A→B→C⇄D→E（`principles.md`）は維持する。ただし Ver.2 では

- A（場所・出来事）: WORLD MAP 上の「場所」そのもの。intro 画面で文章化しない。
- B（困りごと）: 世界の見た目・状態変化で示す（Event State）。
- C（仕事特有の情報・道具）: **盤面上に常時見える**形で置く。
- D（判断・操作）: 最初のタップから始まる。
- E（変化）: WORLD MAP の点灯・道の光・アイテムで返す。

## 3. アイテムの考え方（LOCKED の思想 / 個別アイテムは OPEN）

- 職業そのものを集めるゲームにはしない。
- 考え方: **「出会った仕事の一部を身につける」**。
- ゲームを遊ぶと、その**体験に由来する**アイテムを得る。
- 「白衣＝医師」「コック帽＝調理員」のような**単純な職業コスプレだけにしない**。
  ゲームで実際に体験した「行為」からアイテムを考える。
- 異なる仕事のアイテムを**同時に**身につけてよい。
- これは「あなたは○○向き」ではなく **「これも好き。これも好きかも。」** の可視化。

OPEN（Human Decision 必要）: 具体的なアイテム一覧、獲得条件（クリアで必ず？❤️ を付けた時？）、
装着スロット、レアリティ等の「economy」の有無（→ product-identity-gate: reward / collection 対象）。

## 4. ぼうけんノート / Collection（LOCKED の構造 / 詳細は OPEN）

基本構造:

| タブ | 内容 |
|---|---|
| **であったもの** | 遊んだ社会・仕事・行為の記録 |
| **すきかも** | ユーザー自身が ❤️ をつけたもの |
| **もちもの** | ゲームで獲得し、相棒に装着できるアイテム |

- 通常の「職業図鑑コンプリート」を主目的にしない。
- 意味: **「この子が探検して、こんなものに出会って、こんな『好きかも』を持ち帰ってきた」**
  という冒険の記録。
- 職業カードには、職業名だけでなく
  **「自分がゲームで何をしたか」** と **「それが現実のどんな仕事につながるか」** を
  接続できる構造にする。

Ver.1 との対応: Ver.1 の `ZukanScreen`（しごと図鑑）・`ProfessionScreen`（q2）・
`seeds`（好きの種）が原型。Ver.2 では「すきかも」= ❤️ をつける行為が中心になるため、
Ver.1 の「好きの種 5 択チップ」をそのまま流用するかは OPEN。

OPEN: ❤️ を付けるタイミング（プレイ中？Reveal 後？）、「であったもの」の粒度
（行為単位／場所単位／職業単位）、進捗データの保存形式（Ver.1 の `localStorage`
`jibun-choice-progress-v1` を拡張するか新キーにするか）。

## 5. 最初に作り直す PLAY — 給食 WORLD「栄養・メニュー」（基準ゲーム）

Ver.1 対応: `nutrition-lunch` / `MenuGame.tsx` / `menuLogic.ts`（`drag_and_drop`）。
AS-IS は [audits/ver1-school-lunch-as-is.md](audits/ver1-school-lunch-as-is.md)。

### 実際の仕事の核（LOCKED）

複数の条件を考えながら献立を調整する。

### ゲームの基本（LOCKED）

```
料理を触る / 入れ替える
 ↓ 即座に結果が変わる
 ↓ 「なんで上がった？」
 ↓ また触る
 ↓ より良い献立に近づける
```

- 0/1 の正解判定ではなく、**60〜100 程度の改善型スコア**を想定。
- **複数の高得点解が存在してよい。**
- 難易度は制限時間の短縮ではなく、**実際の仕事の複雑さが増える方向**を検討:

| Lv | 追加される条件 | 状態 |
|---|---|---|
| Lv1 | 栄養 | 検討対象 |
| Lv2 | + 予算 | 検討対象 |
| Lv3 | + 在庫 / 調達 | 検討対象 |
| Lv4 | + 調理条件 | 検討対象 |
| Lv5 | 日ごとの条件変化 | 検討対象 |

（Lv 構成そのものは「検討」であり LOCKED ではない。）

### 実装してはいけないこと（LOCKED）

栄養基準・予算・現実の学校給食条件などの**具体的数値・判定ロジックを推測で実装しない**。
事実確認が必要な部分は `TODO` / `NEEDS_VALIDATION` として残す。

### NEEDS_VALIDATION（着手前に確認が必要な事実）

- 学校給食の栄養基準（学校給食摂取基準）の対象年齢別の値と、ゲームで扱う項目の選び方
- 1 食あたりの材料費の実勢と、予算条件として扱う粒度
- 献立作成で実際に考慮される条件の優先順位（栄養／予算／調達／調理／残食／アレルギー 等）
- 「改善型スコア」の算出根拠（何をどう重み付けするかは専門家確認が必要）
- Ver.1 `menuLogic.ts` の値（nutri/budget/supply/cook の 0〜3 段階）は
  プロトタイプ用の仮値であり、Ver.2 の根拠として流用しない

### Ver.1 からの差分（監査で確認された事実）

- Ver.1 はランダム性なし・失敗状態なし・スコアなし（`isAcceptableSide`= supply≥1 かつ nutri≥1 の 0/1 判定）。
- 判定理由の一部（例: 別産地の価格）は開閉式 InfoCards の中にしか書かれていない。
- 操作はドラッグ＋タップ代替（`useDragDrop`）。Ver.2 でも「触る／入れ替える」は維持する方向。

## 6. 既存ゲームの扱い（LOCKED）

- 現在あるゲームを削除しない。
- Ver.2 の公開導線には未改修ゲームを大量に並べない。
- 給食編 → 1 ゲーム完成 → テスト → 改善 → 次のゲーム、と 1 本ずつ追加する。
- **量より完成度**。
- 既存ゲームは Ver.1 / archive として参照可能にする（`archive/ver1`）。
